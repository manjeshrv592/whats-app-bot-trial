# Database Schema

Full schema at `backend/prisma/schema.prisma`. One Postgres database, two unrelated concerns sharing it: survey data (`users`, `sessions`, `conversation_logs`) and admin login (`AdminUser` and friends, via Better Auth — see [Authentication](../backend/authentication.md) for why they're separate from `User`/`Session` despite the similar names).

## `User` (table: `users`)

One row per WhatsApp phone number — the survey respondent and all their answers, accumulated field-by-field as they progress through the conversation.

```prisma title="backend/prisma/schema.prisma"
model User {
  id                 Int      @id @default(autoincrement())
  phoneNumber        String   @unique @map("phone_number")
  language           String?               // "en" | "kn"
  consented          Boolean?
  name               String?
  travelFrequency    String?  @map("travel_frequency")
  homeArea           String?  @map("home_area")
  originLat          Float?   @map("origin_lat")
  originLng          Float?   @map("origin_lng")
  nearestStation     String?  @map("nearest_station")
  feederMode         String?  @map("feeder_mode")           // home -> nearest station
  destinationStation String?  @map("destination_station")
  distributionMode   String?  @map("distribution_mode")     // exit station -> final destination
  destinationArea    String?  @map("destination_area")
  destLat            Float?   @map("dest_lat")
  destLng            Float?   @map("dest_lng")
  email              String?
  smartCardNumber    String?  @map("smart_card_number")
  createdAt          DateTime @default(now()) @map("created_at")
  updatedAt          DateTime @updatedAt @map("updated_at")

  session          Session?
  conversationLogs ConversationLog[]

  @@map("users")
}
```

Every field is nullable except `id` and `phoneNumber`, because the row is created empty on first contact (via `prisma.user.upsert`) and filled in incrementally as the survey progresses — a respondent who drops out halfway just has a partially-filled row.

**Design note:** this is one row per phone number, i.e. one submission ever. The concept note behind this project mentions weekly re-surveys as a future idea — that would need a separate `responses` table keyed by `(userId, date)`, not built here since it isn't needed yet (see [Known Limitations](../known-limitations.md)).

## `Session` (table: `sessions`)

Tracks *where* a respondent currently is in the conversation — completely separate from `User`'s permanent answer data.

```prisma
model Session {
  id          Int      @id @default(autoincrement())
  phoneNumber String   @unique @map("phone_number")
  currentStep String   @map("current_step")
  createdAt   DateTime @default(now()) @map("created_at")
  updatedAt   DateTime @updatedAt @map("updated_at")

  user User @relation(fields: [phoneNumber], references: [phoneNumber])

  @@map("sessions")
}
```

`currentStep` holds one of the `STEPS` keys from `conversation.js` (e.g. `"ASK_NEAREST_STATION"`), or the terminal values `"DONE"` / `"CANCELLED"`. Splitting this from `User` means a session could theoretically be reset without losing the respondent's already-collected answers.

## `ConversationLog` (table: `conversation_logs`)

A pure audit trail — every inbound and outbound message, in order. Not read by the conversation engine at all; it exists for debugging and for the dashboard's transcript view.

```prisma
model ConversationLog {
  id          Int      @id @default(autoincrement())
  phoneNumber String   @map("phone_number")
  direction   String   // "in" | "out"
  messageText String   @map("message_text")
  createdAt   DateTime @default(now()) @map("created_at")

  user User @relation(fields: [phoneNumber], references: [phoneNumber])

  @@map("conversation_logs")
}
```

For interactive replies (buttons/lists), `messageText` stores the human-readable selected title, not the internal option id. For location messages, it stores `"lat,lng"`.

## Admin auth models (Better Auth)

Generated by `npx @better-auth/cli generate`, not hand-written. See [Authentication](../backend/authentication.md) for the full story on why these have their own table names instead of colliding with `User`/`Session` above.

```prisma
model AdminUser {
  id            String         @id
  name          String
  email         String
  emailVerified Boolean        @default(false)
  image         String?
  createdAt     DateTime       @default(now())
  updatedAt     DateTime       @updatedAt
  adminsessions AdminSession[]
  adminaccounts AdminAccount[]

  @@unique([email])
  @@map("AdminUser")
}

model AdminSession {
  id        String    @id
  expiresAt DateTime
  token     String
  createdAt DateTime  @default(now())
  updatedAt DateTime  @updatedAt
  ipAddress String?
  userAgent String?
  userId    String
  adminuser AdminUser @relation(fields: [userId], references: [id], onDelete: Cascade)

  @@unique([token])
  @@index([userId])
  @@map("AdminSession")
}

model AdminAccount {
  id                    String    @id
  accountId             String
  providerId            String    // "credential" for email/password
  userId                String
  adminuser             AdminUser @relation(fields: [userId], references: [id], onDelete: Cascade)
  password              String?   // hashed — Better Auth manages this, never touched directly
  accessToken           String?
  refreshToken          String?
  idToken               String?
  accessTokenExpiresAt  DateTime?
  refreshTokenExpiresAt DateTime?
  scope                 String?
  createdAt             DateTime  @default(now())
  updatedAt             DateTime  @updatedAt

  @@index([userId])
  @@map("AdminAccount")
}

model AdminVerification {
  id         String   @id
  identifier String
  value      String
  expiresAt  DateTime
  createdAt  DateTime @default(now())
  updatedAt  DateTime @updatedAt

  @@index([identifier])
  @@map("AdminVerification")
}
```

`AdminAccount` is where the hashed password actually lives (under `providerId: "credential"`), not on `AdminUser` itself — that's Better Auth's own modeling choice, mirroring how it'd store an OAuth provider's tokens for the same user if one were ever added.
